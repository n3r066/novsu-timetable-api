# novsu-tg-md-raspis-bot

Бот расписания НовГУ для группы **6381**: парсит серверный HTML портала, отдаёт стабильный JSON через мини-API, следит за изменениями примерно каждые 3 минуты ± 15 секунд и постит **красивые rich-уведомления** в Telegram-канал — что конкретно добавилось, убралось или поменялось.

## Как это работает

```
портал НовГУ (HTML)
      │  curl + случайный Chromium UA, ретраи
      ▼
 fetch.py ──► parse.py ──► content_fingerprint (отпечаток содержимого)
      │                          │
      │                    изменилось?
      │                          ▼
      │                    monitor.py: diff_schedules
      │                          │
      │            ┌─────────────┴─────────────┐
      │            ▼                           ▼
      │   sendRichMessage в канал      edit_dashboard_post
      │   (➕ / ➖ / ✏️ дифф)          (обновить закреп)
      ▼
   api.py (JSON), post.py (пост со скрином), screenshot.py
```

## Модули

| Файл | Что делает |
|---|---|
| `config.py` | `.env`, URL группы, Telegram-цели, `random_ua()` — рандомизация User-Agent через `fake-useragent` (только Chromium-семейство, фоллбек на статичный пул) |
| `fetch.py` | `fetch_html` — curl с `--fail`, 3 ретрая, на каждый ретрай новый UA; `content_fingerprint` — sha256 распарсенного содержимого (иммунитет к волатильным таймстемпам `.xls`-ссылок портала) |
| `parse.py` | HTML → структура `{days, weeks}`; восстанавливает rowspan/colspan, `<tbody>` и вложенный первый `<tr>` реального портала |
| `schedule_logic.py` | Верхняя/нижняя неделя, диапазоны, даты проведения и отмены, «с октября», переход учебного года; view на день/неделю/следующие пары |
| `monitor.py` | **Мониторинг**: `--interval 3 --jitter 0.25` — цикл 3 мин ± 15 с; единый snapshot, text-first доставка, очередь media enhancement и HTML-фоллбек |
| `format.py` | Билдеры rich-сообщений (Bot API 10.2): дашборд-закреп, дифф изменений `build_changes_rich_message`, текстовые фоллбеки |
| `post.py` | Оркестратор постинга: скриншот + caption, stub-сообщения, обновление закрепа |
| `screenshot.py` | Headless Chrome (`google-chrome`): один процесс на пачку скринов через Playwright, PNG по высоте контента, CLI-фоллбек |
| `api.py` | JSON-фасад: `/v1/timetables/...`, `/v1/groups`, `/v1/institutes` |
| `opd.py` | **ОПД по виртуальным группам**: два открытых Google-файла кафедры (таблица ВГ и расписание ВГ) → кто из группы идёт в этот четверг, во сколько (14:00 или 16:00), в какой корпус и аудиторию; кэш `state/opd_cache.json` |
| `telegram_api.py` | Транспорт Bot API: `sendRichMessage` / `editMessageText`, multipart с файлами |

## Мониторинг изменений (главное)

```bash
python3 monitor.py --interval 3 --jitter 0.25   # id закрепа из NOVSU_DASHBOARD_POST_ID
```

- Проверка примерно каждые **3 минуты ± 15 секунд** по времени старта циклов, круглосуточно.
- Сравнение по **отпечатку содержимого** (`content_fingerprint`), а не сырому HTML — смена таймстемпов на `.xls`-ссылках портала не даёт ложных «обновилось».
- При реальном изменении в канал уходит rich-пост, по разделу на день (сводка дня
  называет правки: «Четверг (сменили аудиторию)»), без эмодзи:
  - **таблица дня** «что · занятие · где»: знак `+` `−` `~` `↔` и время пары; предмет,
    вид пары и неделя, преподаватель; аудитория, корпус и формат. Старые значения
    зачёркнуты, новые жирным; у убранной пары зачёркнуты время и место; перенос — одна
    строка «было → стало»; переименование — старое зачёркнуто или подсвечен добавленный хвост
  - свёрнутые **«Подробности: время, недели и примечания»** — таблица «занятие · время и
    недели · примечание» построчно к основной, с правками примечаний «старое → новое»
  - не больше 40 строк на день, остальное названо числом; переходы заглушка↔расписание:
    «Расписание опубликовано» / «Расписание пропало с портала»
- Если `sendRichMessage` недоступен — фоллбек на обычный HTML `sendMessage` (≤4096).
- **Личка** используется только для технических алертов (3 подряд неудачных цикла фетча, отказ постинга) — никакого содержимого расписания.
- Ошибка сети ≠ изменение: состояние не перезаписывается, канал молчит.

Состояние: атомарный `state/monitor_state.json`; `last.json` и `last_parsed.json` сохраняются для совместимости. Неотправленный текстовый дифф остаётся в `pending_notification.json`, а уже доставленные посты, ожидающие скрины, — в FIFO `pending_media.json`.

Один цикл делает один fetch и один parse. Успешная версия сохраняется в SQLite как HTML + parsed JSON и становится общим snapshot для monitor, API группы 6381 и Telegram-постов. API других групп продолжает использовать собственный TTL-fetch.

Уведомление отправляется text-first: rich-текст уходит до запуска Chromium. Затем тот же пост редактируется и получает закрытый блок «Сравнить с порталом: Было / Стало» со slideshow из сохранённых старого и нового HTML snapshots. Если Chromium или media edit временно не работают, текст не дублируется, а enhancement повторяется отдельно.

Чистые скрины кэшируются по SHA-256 от HTML отдельного дня в `state/day_screens/`. Поэтому изменение вторника не перерисовывает понедельник, а один PNG переиспользуется уведомлением и закрепом. Автоочистка держит файлы до 14 дней и ограничивает кэш примерно 200 МБ.

Другие режимы: `python3 monitor.py` — один прогон; `--schedule` — раз в день в 09:00 MSK.

## ОПД по виртуальным группам (четверг)

«Основы проектной деятельности» стоят на портале одним слотом в 14:00 на всю группу,
а реальное занятие идёт по **виртуальным группам (ВГ)**: у каждого студента свои даты,
слот 14:00–15:00 или 16:00–17:00 (свой часовой формат кафедры, не пары портала),
корпус, аудитория и преподаватель. Кафедра публикует
два открытых Google-файла — таблицу ВГ (ФИО → номер ВГ) и расписание ВГ (ВГ → даты).

`opd.py` скачивает оба файла (не чаще раза в 6 часов, `state/opd_cache.json`), разбирает
HTML-экспорт документа с разворачиванием rowspan/colspan (у каждой даты две подколонки —
блок 14:00 и блок 16:00; txt-экспорт их склеивает и путает даты) и добавляет в закреп
для каждого дня с датой из документа сворачиваемый раздел **«ОПД · по виртуальным
группам»**: сворачиваемыми разделами по корпусам (внутри сначала 14:00, потом 16:00,
далее по алфавиту); у каждого студента свой раздел: ВГ · слот · аудитория · преподаватель,
а внутри — состав его виртуальной группы: кто из других академических групп идёт вместе,
из какого института и корпуса (институт берётся из индекса портала; специальности портал
не публикует) и отдельно — у кого занятие отменено. Раздел только про
текущую неделю: ВГ ходят через неделю, и кого нет в таблицах, у того ОПД на этой
неделе нет; чужие даты («далее 01.10») не показываются — пометки только для особых
случаев вроде отмены или «с 15:00». Слот ОПД в таблице дня не рождает «Важно»:
ссылка на объявление кафедры есть в источниках раздела. Блок 16:00 держит четверг в
закрепе до 17:45, хотя портальная пара кончается в 15:45. Без данных (Google
недоступен, кэша нет) закреп рисуется как раньше.

```bash
python3 opd.py                     # ближайший четверг: кто, во сколько, куда
python3 opd.py --date 2026-10-01   # конкретная дата
python3 opd.py --refresh           # скачать файлы заново, игнорируя TTL
```

Ручной запуск от root создаёт root-овый `state/opd_cache.json`; после него нужен
`chown novsu:novsu state/opd_cache.json` (или запуск через `systemd-run --uid=novsu`).
Отключить раздел: `NOVSU_OPD_ENABLED=0`; ссылки на файлы и TTL — `NOVSU_OPD_*` в `config.py`.

## Анти-блокировка портала

Портал novsu.ru режет «неполные» UA (python-requests и т.п.), поэтому:
- фетч только через curl с полным браузерным UA;
- первый запрос использует закреплённый на время процесса профиль iPhone/Safari;
- при ретрае берётся другой полный Chrome/Edge UA (`fake-useragent`, версия ≥120); если пакет недоступен — статичный пул реальных UA;
- интервал проверок джиттерится.

## Systemd-Монитор

В Репозитории Есть Готовый Unit `deploy/novsu-timetable-monitor.service`. Установщик Только Копирует И Включает Unit, Но Намеренно Не Запускает Его До Проверки `.env`:

```bash
sudo ./deploy/install-monitor-service.sh
sudo systemctl start novsu-timetable-monitor.service
sudo systemctl status novsu-timetable-monitor.service
```

Сервис запускает `monitor.py --interval 3 --jitter 0.25` от пользователя `novsu` (`NoNewPrivileges`, `MemoryMax=1G`), перезапускается после сбоя и имеет доступ на запись только к каталогу `state/`. Каталог `state/` принадлежит `novsu`; после ручных прогонов от root верни владельца: `chown -R novsu:novsu state`. После ошибок upstream интервал экспоненциально увеличивается максимум до 20 минут.

## Ролловер закрепа по московскому времени

Закреплённый пост (`message_id` из `NOVSU_DASHBOARD_POST_ID`, сейчас `184`) показывает только актуальные дни учебной недели. Сегодняшний день исчезает после окончания последней применимой пары, остальные прошедшие дни — при смене даты по Москве:

- в пятницу в разделе остаются `Пятница` и `Суббота`, прошедшие пн–чт исчезают;
- подпись раздела меняется с `Полное расписание` на `Расписание до конца недели`, чтобы не обещать лишнего;
- скрины прошедших дней в пост не грузятся (кеш `state/dashboard_screens.json` при этом хранит все дни недели);
- в ночь на воскресенье фокус уезжает на понедельник: пост сам переключается на следующую неделю и показывает её целиком.

Кто дёргает обновление:

- monitor вычисляет `presentation_fingerprint` и вызывает Telegram edit только при смене расписания, текущего набора дней или учебной недели;
- отдельный rollover timer не нужен: трёхминутный monitor замечает полночь, окончание последней пары и переход недели через единый `resolve_dashboard_view()`;
- вручную: `python3 post.py --roll` (id из `.env`) или `python3 post.py --roll <MESSAGE_ID>`.

Логика: `schedule_logic.visible_week_days()` (имя дня берётся из реальной даты — неделя 1 начинается во вторник 01.09, а не в понедельник), `format._day_not_past()` и фильтр скринов в `post.edit_dashboard_post()`. «Сегодня» всегда считается по Москве (`post._today_msk()`), хотя сервер живёт в UTC.

## API

```text
GET /health
GET /v1/institutes
GET /v1/groups?q=6381
GET /v1/timetables/6381
GET /v1/timetables/6381/day?date=tomorrow
GET /v1/timetables/6381/week?week=2
GET /v1/timetables/6381/week?mode=auto
GET /v1/timetables/6381/week?mode=auto&date=2026-09-13
GET /v1/timetables/6381/next?date=2026-09-07&time=09:30&limit=3
```

Полное расписание содержит `schema_version`, `group`, `source_url`, `snapshot_id`, `fetched_at`, `schedule.days`. Недельный ответ содержит выбранную `week`, её `days`, `summary` и `source_url`.

`/week?mode=auto` выбирает неделю по сегодняшней московской дате. Если дата попала в промежуток календаря (обычно воскресенье) или ещё не наступила первая неделя, возвращается ближайшая будущая опубликованная неделя. Например, `date=2026-09-13` выбирает неделю 3. Если воскресенье входит в опубликованный интервал, остаётся текущая неделя. Время окончания пар не влияет на выбор. Параметр `date` поддерживает обычные форматы API, включая `today`, `tomorrow` и `YYYY-MM-DD`.

После последней даты календаря автоматический режим возвращает `404` с `{"error":"calendar_ended","calendar_end":"2026-12-31"}` (дата берётся с портала). Без доступного календаря возвращается `404` с `{"error":"calendar_unavailable"}`. Подтверждённая заглушка портала по-прежнему возвращает `200` и `stub: true`.

Существующие запросы не изменены: `week=2` всегда выбирает вторую неделю из загруженного календаря; `/week` без `mode` выбирает только неделю, содержащую указанную дату, и может вернуть `week_not_found` в воскресенье. Одновременно задавать `mode=auto` и `week` нельзя; неизвестный, пустой или повторный `mode` возвращает `400 bad_request`. Режим `auto` доступен только для `/week` и не меняет правила обновления/свежести снимков.

Прочие ошибки: `404` (роут/группа), `502` `{"error":"upstream_or_parse_failure"}` при падении фетча/парса/валидации. Снапшоты и нормализованные пары пишутся в `state/timetable.sqlite3` (`db/schema.sql`). Сервис без аутентификации — держать на loopback/приватной сети.

## Запуск

```bash
pip install -r requirements.txt      # beautifulsoup4, pillow, fake-useragent
python3 -m pytest -q                 # тесты
python3 api.py --once                # разовый JSON группы 6381
python3 api.py --host 127.0.0.1 --port 8787
# или установить systemd-юниты (monitor + API + hourly healthcheck)
sudo ./deploy/install-monitor-service.sh
python3 monitor.py --interval 3 --jitter 0.25  # мониторинг + уведомления в канал
python3 post.py --force              # пост расписания со скрином
```

`.env` (в репо не лежит):

```
TG_BOT_TOKEN=...            # бот канала, закрепа и алертов
TG_CHANNEL_ID=-100...
TG_DM_TARGET=...
NOVSU_DASHBOARD_POST_ID=... # id закреплённого поста, который редактирует монитор
```

Сервис ведёт только группу **6381** (`inst_id=2244947`, `type=ДО`, `year=2026`). API отдаёт `404` для других групп, `/v1/groups` и `/v1/institutes`; `default`/`me`/пустая группа означают 6381. Снять ограничение можно переменной `NOVSU_API_DEFAULT_GROUP_ONLY=0`.

## Данные и парсер

- `data/annotations.json` — версионированный словарь сокращений (ДОТ, лек., пр., лаб., ауд., подгр.) и правила пометок.
- `knowledge/schedule_notes.json` — правила показа примечаний в закрепе: обычные места и короткие даты идут прямо в строку пары, списки дат, отмены и неизвестные формулировки остаются в закрытом разделе `Важно`.
- Общий DOM-обход восстанавливает реальный вложенный первый `<tr>`, обычные `<tbody>/<thead>`, `rowspan` и `colspan`; новый day-разделитель перекрывает протухший `rowspan`.
- Колонки определяются по нормализованным заголовкам, а `под гр.` и `комм.` допускаются как необязательные.
- Валидация: число распарсенных пар обязано совпасть с числом физических строк-пар в HTML, иначе `502` (никаких частичных данных).

## Тесты

```bash
python3 -m pytest -q
```

Покрыто: парсер (rowspan, заглушки, структурирование комментариев), дата-логика (верх/низ, «с …», «только …»), fetch (ротация UA, `--fail`, ретраи, стабильность отпечатка), monitor (дифф add/remove/change, stub-переходы, тишина при сетевых ошибках и волатильных таймстемпах, фоллбек постинга), rich-форматирование (структура блоков, лимиты 4096/1024, экранирование HTML).
